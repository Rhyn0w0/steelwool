# SteelWool

SteelWool is a [Fabric](https://fabricmc.net/) mod for Minecraft that acts as a **translation layer for [NeoForge](https://neoforged.net/) mods**.

## Goal

When SteelWool is installed and loaded by Fabric, it looks for a `neoforge` folder inside the game's `mods` folder and loads every NeoForge mod in it **as if it were a Fabric mod**. Players can then run NeoForge mods next to their Fabric mods without switching mod loaders.

```
.minecraft/
└── mods/
    ├── fabric-api-x.y.z.jar     <- required by SteelWool
    ├── steelwool-x.y.z.jar      <- SteelWool (a normal Fabric mod)
    ├── some-fabric-mod.jar      <- loaded by Fabric as usual
    └── neoforge/                <- SteelWool scans this folder
        ├── some-neoforge-mod.jar
        └── another-neoforge-mod.jar
```

Fabric only scans the top level of `mods/`, so it never sees the jars in `mods/neoforge/`.

## Status

**Version 0.1.0: first working version.** It targets **Minecraft 26.3**, Fabric Loader 0.20.1+, Fabric API and NeoForge **26.3.0.x** mods. It needs Java 25.

Verified:

- NeoForge's official example mod (the [26.3 MDK](https://github.com/NeoForgeMDKs/MDK-26.3-ModDevGradle)), built unmodified with NeoForge's own tooling, loads and runs on a Fabric dedicated server. This covers its block, item, creative tab, config file, common setup and server-starting event.
- The project's test mod ([`testmod/`](testmod/)) passes 13 automated in-game tests on a dedicated server: registration, lifecycle events, `@EventBusSubscriber`, config, data packs, commands, mod file metadata, payload registration and a mixin from the NeoForge mod.
- The built `steelwool-0.1.0.jar` works in a real (non-development) Fabric server install.
- 6 of 35 popular NeoForge mods from Modrinth start on a dedicated server: Cloth Config, Vein Miner, No Chat Reports, Kotlin for Forge, FerriteCore and GeckoLib. See [Compatibility with real mods](#compatibility-with-real-mods).

Not yet verified: the client. SteelWool loads NeoForge mods and their resource packs on the client, but the automated client test (`runClientGameTest`) could not render a window in the environment where it was developed.

Expect most real-world NeoForge mods to fail for now. Many use NeoForge APIs that SteelWool does not implement yet (see [What is supported](#what-is-supported)). When a mod needs one, SteelWool stops with a message naming the mod and the missing NeoForge class or method.

## How it works

Minecraft 26.x ships unobfuscated, so NeoForge mods and Fabric run against the same class names. SteelWool therefore does not remap anything. It does three things:

1. **Loads the jars.** Fabric's `preLaunch` entrypoint ([`SteelWoolLoader.discoverAndAttach`](src/main/java/dev/steelwool/loading/SteelWoolLoader.java)) reads each jar in `mods/neoforge/`:
   - It parses `META-INF/neoforge.mods.toml`.
   - It finds `@Mod` and `@EventBusSubscriber` classes by reading the bytecode, without loading the classes.
   - It extracts any jars bundled inside (jar-in-jar). Jars without a `neoforge.mods.toml` that are libraries (`FMLModType: LIBRARY` / `GAMELIBRARY`) or only bundle other jars, like Kotlin for Forge, go on the class path too.
   - It checks required and incompatible dependencies against both NeoForge and Fabric mods.

   It then adds the jars to the game class path and registers their mixin configs with Fabric's Mixin. It translates each mod's access transformers (`META-INF/accesstransformer.cfg`) into Fabric access widener entries, which Fabric applies as classes load.
2. **Re-implements the NeoForge API.** The classes NeoForge mods call (`net.neoforged.*`) are written fresh in SteelWool, with the same names and signatures:
   - The mod loading lifecycle runs on top of Fabric's entrypoints.
   - Registration (`DeferredRegister`, `RegisterEvent`) runs inside Fabric's normal registration window.
   - Game events are posted from Fabric API callbacks (`dev.steelwool.bridge`).
   - NeoForge's event bus is a standalone library, so SteelWool ships the real one.
3. **Adds what NeoForge adds to Minecraft.** NeoForge changes Minecraft's own classes. It adds about 1,400 public members and 128 "extension" interfaces, and mods compiled against NeoForge call them. SteelWool adds them back as Fabric mixins in `dev.steelwool.mixin.patch`. Static methods, which Mixin cannot add, are generated by [`SteelWoolMixinPlugin`](src/main/java/dev/steelwool/mixin/SteelWoolMixinPlugin.java). So far this covers the creative-tab additions the MDK uses.

Each NeoForge mod jar is also added as an always-enabled built-in pack. Its `data/` folder becomes a server data pack and its `assets/` folder a client resource pack.

### Lifecycle mapping

| NeoForge | When SteelWool fires it |
|---|---|
| `@Mod` constructor (gets `IEventBus`, `ModContainer`, `Dist`), `FMLConstructModEvent` | Fabric `main` entrypoint |
| Configs loaded → `ModConfigEvent.Loading` | Fabric `main`, after construction |
| `RegisterEvent` (every registry, NeoForge's order) | Fabric `main` |
| `FMLCommonSetupEvent` (+ `enqueueWork`) | Fabric `main` |
| `FMLClientSetupEvent` / `FMLDedicatedServerSetupEvent` | Fabric `client` / `server` entrypoint |
| `InterModEnqueueEvent`, `InterModProcessEvent`, `FMLLoadCompleteEvent` | Right after side setup |
| `ServerAboutToStartEvent` | Fabric `SERVER_STARTING` |
| `ServerStartingEvent`, `ServerStartedEvent` | Fabric `SERVER_STARTED` |
| `ServerStoppingEvent` / `ServerStoppedEvent` | Fabric `SERVER_STOPPING` / `SERVER_STOPPED` |
| `RegisterCommandsEvent` | Fabric `CommandRegistrationCallback` |
| `RegisterPayloadHandlersEvent` | Fabric `main`, after common setup |
| `RegisterClientPayloadHandlersEvent` | Fabric `client`, before client setup |
| `BuildCreativeModeTabContentsEvent` | Fabric `CreativeModeTabEvents.MODIFY_OUTPUT_ALL` |

## What is supported

| Area | Supported | Not yet |
|---|---|---|
| Mod loading | `neoforge.mods.toml` (mods, dependencies, mixins), `@Mod` (incl. `dist`), `@EventBusSubscriber`, jar-in-jar, library jars, access transformers (widening only), `javafml` and `kotlinforforge` mods, `ModList` (incl. mod files and annotation scan data), `LoadingModList`, `FMLLoader`, `IModInfo`/`IModFileInfo`/`IModFile`, `ModLoadingContext`, `FMLEnvironment`, `FMLPaths`, `FMLConfig` (defaults only), `InterModComms`, `LogicalSide`/`EffectiveSide`, `ObfuscationReflectionHelper` | Dependency version range checks, mod ordering, other language providers, coremods, access transformers that narrow access or target classes loaded before `preLaunch` |
| Events | NeoForge's real event bus (`IEventBus`, `@SubscribeEvent`, priorities, cancellation), the lifecycle and game events in the table above | All other NeoForge game events (player, entity, level, tick, render, input, …) |
| Registries | `DeferredRegister` (+ `.Items`, `.Blocks`, `.DataComponents`, `.Entities`), `DeferredHolder`/`DeferredItem`/`DeferredBlock`, `RegisterEvent` | Custom registries (`makeRegistry`, `NewRegistryEvent`), aliases, data maps, datapack registries |
| Config | `ModConfigSpec` (booleans, numbers with ranges, strings, enums, lists, comments, sections), TOML files in `config/` | Per-world `SYNCED` configs and syncing them to clients, the in-game config screen (a placeholder screen points to the file) |
| Resources | Mod `assets/` and `data/` as built-in packs | Pack overlays and `pack.mcmeta` features |
| Patched Minecraft | `CreativeModeTab.builder()` and NeoForge's `CreativeModeTab.Builder` methods (tab ordering and styling are accepted but not applied) | The other ~1,400 NeoForge additions and extension interfaces (`IItemExtension`, `IBlockExtension`, …) |
| Networking | `RegisterPayloadHandlersEvent`, `PayloadRegistrar` (play, configuration and common payloads), `IPayloadContext`, `PacketDistributor`, `ClientPacketDistributor`, `RegisterClientPayloadHandlersEvent`, on top of Fabric's networking API | Version and `optional()` negotiation, network-thread handlers (they run on the main thread), configuration tasks |
| Other NeoForge systems | | Capabilities, data attachments, fluids (`FluidType`), client rendering/model hooks, key mappings, data generation |

## Installing

To try it out, the easiest way is the test bundle (`./gradlew testBundle`, or the `steelwool-test-bundle` artifact from CI). It contains everything needed, plus [step-by-step testing instructions](testing/INSTRUCTIONS.md). To install by hand:

1. Install Fabric Loader for Minecraft 26.3, plus [Fabric API](https://modrinth.com/mod/fabric-api).
2. Put `steelwool-<version>.jar` in `mods/`.
3. Start the game once. SteelWool creates `mods/neoforge/`.
4. Put NeoForge mod jars in `mods/neoforge/` and start the game again.

The log lists what SteelWool found (`Found N NeoForge mod(s) in …`) and why it skipped any jar.

## Developing

### Requirements

- **JDK 25.** Gradle's daemon is pinned to Java 25 (`gradle/gradle-daemon-jvm.properties`), and the Foojay plugin downloads a matching JDK if none is installed. To use an existing JDK, set `JAVA_HOME` to it, for example `JAVA_HOME=/opt/homebrew/opt/openjdk@25` from `brew install openjdk@25`.
- Internet access on the first build: Gradle downloads Minecraft, Fabric and NeoForge.

### Commands

| Command | What it does |
|---|---|
| `./gradlew build` | Compiles, runs the unit tests and the dedicated-server game tests, and builds `build/libs/steelwool-<version>.jar`. CI runs this. |
| `./gradlew test` | Unit tests only (`src/test`), no Minecraft needed. Fast. |
| `./gradlew runGameTest` | Boots a dedicated server with SteelWool and the test NeoForge mod, runs the game tests (`src/gametest`) and exits. |
| `./gradlew runClientGameTest` | The same on the client (opens a game window). |
| `./gradlew testBundle` | Builds `build/distributions/steelwool-test-bundle-<version>.zip`: SteelWool, Fabric API, the Fabric installer, the test NeoForge mod and [testing instructions](testing/INSTRUCTIONS.md) for trying it in a normal Minecraft install. |
| `./gradlew runServer` / `runClient` | Runs the game in `run/`. Put NeoForge mod jars in `run/mods/neoforge/`. |

The first `runGameTest` or `build` also builds the test mod. This runs NeoForge's ModDevGradle setup, which decompiles and patches Minecraft and takes a few minutes. Later runs are cached.

### Compatibility with real mods

[`compat/mods.json`](compat/mods.json) lists about 35 popular NeoForge 26.3 mods from Modrinth. [`compat/compat_check.py`](compat/compat_check.py) does the following for each one:

1. Downloads the mod and its required dependencies.
2. Starts a fresh Fabric dedicated server with SteelWool and only that mod in `mods/neoforge/`.
3. Records whether the server finishes starting. If it doesn't, it records why: a missing NeoForge API, a failed mixin, a missing dependency or a crash.

To run it, use `./gradlew testBundle && python3 compat/compat_check.py [slug ...]`. It needs Python 3.10+ and Java 25. The results go to `build/compat/report.md`, with one log per mod. To test the checker itself, run `python3 -m unittest discover compat`.

The [compat workflow](.github/workflows/compat.yml) runs on pull requests, on pushes to `main`, every Monday and on demand. The report appears in the run summary. The workflow fails only if a mod marked `"expect": "pass"` stops loading. When the report shows a new mod passing, set its `expect` to `pass`. The "Missing NeoForge APIs" table at the end of the report is the to-do list for SteelWool.

The report only shows the first missing class each mod hits. To see everything a mod uses that SteelWool lacks, run `python3 compat/missing_api.py [--members] build/libs/steelwool-<version>.jar <mod.jar> ...` (the compat check saves the jars under `build/compat/downloads/`). It reads the mod's bytecode and lists each missing `net.neoforged` class and member, with the mods that use it.

### Releasing

1. Set `mod_version` in `gradle.properties` (for example `0.2.0`) and merge to `main`.
2. Tag and push: `git tag v0.2.0 && git push origin v0.2.0`.

The [release workflow](.github/workflows/release.yml) builds and tests the mod. It then publishes a GitHub release with `steelwool-<version>.jar` and `steelwool-test-bundle-<version>.zip` attached. It fails if the tag doesn't match `mod_version`, and marks `0.x` versions as pre-releases.

### Project layout

```
src/main/java/dev/steelwool/     SteelWool itself
  discovery/                     find + parse NeoForge mod jars (no Minecraft classes)
  loading/                       mod lifecycle driver (SteelWoolLoader)
  bridge/                        Fabric API callbacks -> NeoForge events
  config/                        config file loading
  resource/                      mod jars as resource / data packs
  mixin/                         SteelWool's mixins; mixin/patch/ = NeoForge's Minecraft patches
  patch/                         static methods added to Minecraft classes
src/main/java/net/neoforged/     SteelWool's re-implementation of the NeoForge / FML API
src/test/                        JUnit tests
src/gametest/                    in-game tests (Fabric game test API)
testmod/                         a NeoForge mod built with NeoForge's own tooling (separate Gradle build)
compat/                          popular NeoForge mods to check against (mods.json + compat_check.py)
```

### Adding support for a NeoForge API

1. Find what a mod needs. SteelWool's error names the missing `net.neoforged` class or method. NeoForge's sources are at `https://maven.neoforged.net/releases/net/neoforged/neoforge/<version>/neoforge-<version>-sources.jar`.
2. Add the class under `src/main/java/net/neoforged/...` with **exactly** NeoForge's package, name and method signatures. Mods are linked against them by descriptor, so a different return type breaks them. Implement it on top of Fabric API where possible.
3. If the mod calls a method that NeoForge adds to a Minecraft class, add it in `dev.steelwool.mixin.patch`. To list every such method, compare vanilla Minecraft with the patched jar the test mod build produces (`testmod/build/moddev/artifacts/minecraft-patched-<version>.jar`).
4. Use the feature in [`testmod/`](testmod/) and add a game test in `src/gametest/`. Add unit tests in `src/test/` for logic that doesn't need Minecraft.

## Prior art

| Project | Direction | Notes |
|---|---|---|
| [Kilt](https://github.com/KiltMC/Kilt) | (Neo)Forge mods on Fabric | The closest project. Active, alpha/beta, Minecraft 1.21.1 (1.20.1 end-of-life, 26.1 port in progress). Bundles forked NeoForge/FML/EventBus. Scans the normal `mods/` folder. |
| [Patchwork](https://github.com/PatchworkMC/patchwork-api) | Forge mods on Fabric | Minecraft 1.14–1.16, archived in 2024. Needed to remap names between Forge and Fabric (SRG to Intermediary); 26.x no longer needs that. |
| [Sinytra Connector](https://github.com/Sinytra/Connector) | Fabric mods on NeoForge (the reverse) | Mature. Re-implements Fabric API on NeoForge ("Forgified Fabric API") and rewrites mixins where NeoForge's patches change signatures. |

Lessons SteelWool builds on:

- Translating the loader APIs is the easy part. Most of the work is NeoForge's patches to Minecraft and its large subsystems: capabilities, networking, fluids and rendering.
- Keeping up with new versions is what stalled earlier projects. SteelWool targets only unobfuscated 26.x and builds its test mod with NeoForge's own tooling, so each NeoForge update can be checked mechanically.
